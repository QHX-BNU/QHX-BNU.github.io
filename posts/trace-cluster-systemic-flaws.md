## 问题

评测 Agent 时最头疼的一类情况：单条 Trace 看起来问题不大——某个工具调用参数写错了、某次检索没找到需要的信息、某个子任务被提前放弃。这些都是"小毛病"，修一个少一个。

但有个疑问一直没解决：**这些小毛病是随机的噪声，还是同一个系统性缺陷的不同表现？**

如果是后者，逐条修 Trace 就是在做无用功——根因不除，同样的失败会换着花样出现。

## 初步假设

一个可检验的假设：把连续多天（比如一周）的失败 Trace 拿出来做聚类，如果某些失败模式**跨天稳定复现**，那它们大概率来自系统层面（提示词设计、工具接口、上下文管理），而不是模型的随机波动。

关键区分标准：

- **随机噪声**：失败模式在时间上均匀分布，聚类后没有明显的簇
- **系统性缺陷**：同一种失败模式每天都会出现，且比例相对稳定

## 实验设计的草稿

1. 采集至少 7 天的失败 Trace（失败的定义本身就需要先想清楚）
2. 用 LLM 把每条失败 Trace 归纳成结构化的失败描述（这一步的 prompt 很关键）
3. 对失败描述做聚类，观察簇的数量和跨天分布
4. 对照实验：对成功 Trace 也做同样处理，看"系统性模式"是否只出现在失败侧

## 可能的失败原因

- 失败描述这一步本身引入偏差：不同的 Trace 可能被归纳成相似但本质不同的描述
- 样本量不够，跨天复现可能只是巧合
- 系统性缺陷的定义太模糊，最后变成循环论证
